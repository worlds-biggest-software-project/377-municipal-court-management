# Data Model Suggestion 2: Hybrid Relational + JSONB

> Project: Municipal Court Management · Created: 2026-05-26

## Philosophy

This model collapses the municipal court domain into five core tables by using JSONB columns to aggregate related data within natural operational boundaries. Each table represents a primary aggregate: `courts` (configuration, staff, fee schedules, courtroom setup), `defendants` (identity with embedded case summaries and financial overview), `cases` (the central aggregate embedding hearings, disposition, fines, payments, documents, and warrants), `notifications` (outbound communication log), and `ai_suggestions`. An `audit_log` table completes the set.

The key insight is that municipal court operations centre on two lookups: the case and the defendant. A clerk at the counter needs the full case picture (charge, hearing schedule, disposition, fines owed, payments made, warrants, documents) in one view. A defendant at the portal needs their account summary (active cases, balances, upcoming hearings, warrant status). By embedding hearing history, disposition, financial ledger, documents, and warrant status inside the case aggregate, and embedding an active-cases summary inside the defendant aggregate, both lookups become single-row reads.

This approach suits small to mid-size municipal courts (sub-50k population) that prioritise rapid deployment and flexible jurisdiction-specific configuration over NIEM entity purity. State reporting exports are generated by extracting and transforming JSONB fields at the application layer.

**Best for:** Small municipalities prioritising rapid deployment, flexible statute/fee configuration, and minimal schema migration overhead.

**Trade-offs:**
- Pro: Full case view (charge, hearings, disposition, fines, payments, warrants, documents) is a single-row read
- Pro: Defendant account summary is a single-row read — ideal for public portal
- Pro: Jurisdiction-specific statutes, fee schedules, and reporting codes require no schema changes
- Pro: Adding new case types, fine categories, or hearing types is a configuration change, not a migration
- Con: Cross-case analytics (aggregate revenue, clearance rates) require JSONB extraction
- Con: JSONB fields bypass CHECK constraints — validation at the application layer
- Con: NIEM/ECF entity mapping requires API-layer decomposition
- Con: Cases with extremely long financial histories (100+ payment transactions) may have large rows

## Standards Alignment

| Standard | How It's Used |
|----------|---------------|
| NIEM Justice Domain | Case and defendant entities in JSONB; API layer decomposes to NIEM structures for exchange |
| OASIS LegalXML ECF 5.01 | ECF filing identifiers stored in `cases.ecf_json`; API maps to ECF messages |
| NCSC JTC Functional Standards | All NCSC functional areas (initiation, calendaring, disposition, financials) covered within case aggregate |
| CJIS Security Policy | `audit_log` with CJIS flags; warrant NCIC tracking in `cases.warrants_json` |
| NIST SP 800-53 | Audit controls satisfied by partitioned audit_log |
| PCI-DSS v4.0 | Payment processor references only in `cases.payments_json` — no card data |
| WCAG 2.1 AA | `notifications` supports multilingual content |
| ISO 15489 | Document retention metadata in `cases.documents_json[].retention` |
| PDF/A (ISO 19005) | Document format tracking in `cases.documents_json[].format` |

## Aggregate Query Examples

### Full case view (single-row read)

```sql
SELECT case_number, case_type, status, charge_json, filing_json,
       hearings_json, disposition_json, fines_json, payments_json,
       payment_plan_json, balance_cents, warrants_json, documents_json,
       dmv_json, retention_json
FROM cases
WHERE court_id = $1 AND id = $2;
```

### Defendant portal account (single-row read)

```sql
SELECT identity_json, portal_json, cases_json, financial_json, warrants_json
FROM defendants
WHERE court_id = $1 AND id = $2;
```

### Cases with active warrants

```sql
SELECT id, case_number, case_type, defendant_id, warrants_json
FROM cases
WHERE court_id = $1
  AND warrants_json @> '[{"status": "active"}]';
```

### Today's docket

```sql
SELECT c.case_number, c.case_type,
       d.identity_json->>'last_name' AS defendant_last,
       d.identity_json->>'first_name' AS defendant_first,
       c.charge_json->>'statute_description' AS charge
FROM cases c
JOIN defendants d ON d.id = c.defendant_id
WHERE c.court_id = $1
  AND c.next_hearing_date::DATE = CURRENT_DATE
ORDER BY c.next_hearing_date;
```

## Key Design Decisions

1. **Case as the central aggregate** — hearings, disposition, fines, payments, warrants, and documents are all embedded within the case row because the clerk's primary workflow operates case-by-case. One GET returns everything needed for any case action.

2. **Defendant summary as a derived view** — `defendants.cases_json` is a denormalised summary of active cases. The case aggregate is the source of truth; the defendant summary is updated whenever a case changes. This keeps the defendant portal fast without a multi-table JOIN.

3. **Fee schedule in court JSONB** — municipal fee schedules vary by jurisdiction and change with legislation. Embedding them as JSONB in the court row means fee changes are a simple JSON update, not a schema migration. Historical fee schedules are preserved in the audit log.

4. **Staff in court JSONB** — for courts with 5-20 staff, embedding users in `courts.staff_json` avoids a separate table. Authentication still delegates to SAML/OIDC; the JSONB stores role assignments and CJIS certification status.

5. **Hearing history as case JSONB array** — the full hearing timeline (including continuances, no-shows, and outcomes) is embedded in `cases.hearings_json`. Continuance chains are tracked by `continued_from` references within the array.

6. **Payment plan in case JSONB** — payment plans are case-specific and simple (monthly amount, start/end date). Embedding avoids a separate table while keeping plan status immediately visible in the case view.

7. **Warrant tracking in case JSONB** — warrants are tightly coupled to cases. NCIC entry numbers and DMV hold status are tracked within the warrant JSONB, enabling the clerk to see the full enforcement picture in the case view.

8. **Notifications as a separate table** — unlike other entities embedded in aggregates, notifications need independent lifecycle tracking (pending → sent → delivered/failed) and provider reference storage. They also serve as the communication audit trail.

9. **PCI compliance by exclusion** — `payments_json` stores processor names and reference IDs but never card data. The payment flow delegates to the configured processor (Stripe, nCourt) via redirect/iframe.

10. **NIEM/ECF at the API layer** — NIEM CaseID and ECF FilingIdentifier are stored in `filing_json` and `documents_json[].ecf_doc_id`. The API layer transforms between JSONB aggregates and NIEM/ECF XML messages for state reporting and e-filing integration.
